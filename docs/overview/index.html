Stack decisions and why

ChoiceReasoning
Plain JavaScript, not TypeScriptMy strongest comfort is in MERN-style JavaScript. The assessment only asked for Node.js — nothing required TypeScript, so I used the stack I could reason about fastest and most correctly under time pressure.
MongoDB over PostgreSQLMy existing project background is MERN, so MongoDB let me move faster. MongoDB Atlas runs as a replica set, which gives real multi-document transactions, and I used a partial unique index to get the same "only one active spin per room" guarantee a relational unique constraint would give — so I didn't lose correctness by choosing Mongo.
AWS EC2 over a serverless optionEC2 gives a fixed (Elastic) IP address. That let me restrict my MongoDB Atlas database to accept connections from exactly one IP, instead of opening it to the whole internet — which a dynamic-IP serverless platform would have forced me to do.
Docker + NginxDocker packages the app so it runs identically anywhere. Nginx sits in front as a reverse proxy, adding security headers and rate limiting, and routing traffic to the right place.
03

Architecture — How It Actually Works

When a request reaches the server, it hits Nginx first. Nginx either serves the static test-client page directly, or forwards the request to the Node application running behind it. The Node app talks to MongoDB Atlas, hosted separately in the cloud.

The full user journey

1
Create a user — a display name is submitted, the server returns a signed JWT token. That token proves identity on every future request without hitting the database each time.
2
Create or join a room — creating a room makes you its owner and an active member in one atomic step. Joining is idempotent: joining twice doesn't create a duplicate membership.
3
Connect over Socket.IO — the client opens a persistent real-time connection, authenticated with the same JWT. It immediately receives a room_state snapshot.
4
Draft sharing — a draft's metadata can be shared into the room, broadcast live to everyone connected as draft_shared.
5
Spin starts — the room owner triggers it. The server snapshots exactly who is eligible at that instant, inside one atomic transaction, so a person joining at the same moment can't create a half-counted state.
6
Eliminations tick every 5 seconds — one random participant is eliminated per tick, broadcast as user_eliminated, until exactly one remains and winner_announced fires.

The single most important design decision

The rule "only one spin can be active per room" is enforced inside the database itself, using a MongoDB partial unique index scoped to the WAITING and RUNNING statuses. This means even if two start-spin requests arrive in the same millisecond, MongoDB itself rejects the second one — the guarantee doesn't rely on application code getting a timing check exactly right.

{ roomId: 1 }, { unique: true, partialFilterExpression: { status: { $in: ['WAITING','RUNNING'] } } }

The elimination timer

Instead of a simple repeating timer, each elimination schedules the next one by reading a persisted timestamp from the database and calculating the exact remaining delay. This keeps the 5-second cadence accurate even if a database write happens to be briefly slow — a fixed interval timer would drift under that condition.

Recovering from a crash

If the server process restarts while a spin is running — a real crash, or a deliberate restart during deployment — it checks the database on boot for any spin left in a running state and resumes it automatically from the exact point it was interrupted, rather than leaving the room stuck.

04

How This Was Tested

The system is covered by 22 automated tests (unit and integration) that run against a real MongoDB test database — not mocks — including all seven edge cases specified in the assessment (duplicate spin starts, a player leaving mid-spin, reconnect recovery, owner disconnect, insufficient players, a real server restart mid-spin, and concurrent joins at the moment a spin starts).

It was also manually tested end-to-end using a small browser-based test client with three separate connected users, and verified live on the deployed AWS endpoint, not just locally.

Testing it yourself

There's no sign-up screen in the test client — it expects a token. Here's a copy-paste way to generate real users, a room, and try the live system directly:

curl -X POST http://51.20.248.170/api/v1/users -H "Content-Type: application/json" -d '{"displayName":"Reviewer-A"}'
curl -X POST http://51.20.248.170/api/v1/users -H "Content-Type: application/json" -d '{"displayName":"Reviewer-B"}'
curl -X POST http://51.20.248.170/api/v1/users -H "Content-Type: application/json" -d '{"displayName":"Reviewer-C"}'

# copy each "token" from the responses above, then:
curl -X POST http://51.20.248.170/api/v1/rooms -H "Authorization: Bearer <TOKEN_A>" -H "Content-Type: application/json" -d '{"name":"Review Room"}'
# copy the room "id" from the response, then join with B and C:
curl -X POST http://51.20.248.170/api/v1/rooms/<ROOM_ID>/join -H "Authorization: Bearer <TOKEN_B>"
curl -X POST http://51.20.248.170/api/v1/rooms/<ROOM_ID>/join -H "Authorization: Bearer <TOKEN_C>"

Then open http://51.20.248.170/ui/ in three browser tabs, paste in the matching token and room ID in each, connect, and start a spin as Reviewer-A to see the full live flow — including the 5-second elimination cadence.

Problems I ran into while building this

  • A socket connection issue that silently hung instead of failing — traced to a security-header configuration blocking local test requests, plus an authentication path that could hang if something went wrong mid-check. I added a timeout guard so this class of failure can never hang silently again.
  • Socket event names initially didn't match the assessment's exact required names — caught this on a careful second read of the spec and corrected every one.
  • Learning Docker and AWS EC2 deployment from scratch within the time available was the single biggest constraint — I got it working, but I'd want more time to harden the deployment further (see below).

What I would improve with more time

  • Move the in-memory spin timer to a Redis-backed scheduler, so the service could run as more than one instance without risking duplicate eliminations.
  • Add HTTPS via a proper domain and certificate, instead of a plain HTTP IP endpoint.
  • Build a small dedicated frontend for testing instead of the current bare-bones manual client.
  • Add more granular rate limiting per-user rather than per-IP only.
I'd rather state these gaps clearly than have them discovered during review. I'm confident I can walk through and defend every decision above in detail.
